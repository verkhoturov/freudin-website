# QA-агент: проверка интерфейса

Как закрывать шаг плана с интерфейсом (правило 14 в [`process.md`](process.md), решение 26
в [`docs/DECISIONS.md`](../DECISIONS.md)).

QA-агент opencode проверяет работающий интерфейс по критериям. Конфиг —
`~/.config/opencode/agents/qa.md`: агент работает через `agent-browser`, код не меняет
и серверы не запускает.

## Цикл шага плана с QA

Сделав шаг или подшаг 🤖 из карточки этапа по ссылке в `docs/PLAN.md`, который меняет поведение или вид интерфейса,
не отмечай его сразу, а пройди цикл:

1. Проверки из правила 5 [`process.md`](process.md) (`lint:fix`, `typecheck`, `npm test`)
   прошли.
2. **Бриф.** Критерии берутся из карточки шага: сценарий, «Готово, когда», размеры экрана. Каждый
   критерий — проверяемое действие и ожидаемый результат с селектором и числом, где они есть
   («ширина `textarea[name=bio]` ≥ 360 px», а не «колонка ~448 px»).
3. **Запуск** QA-агента (команды ниже) и разбор отчёта. Скриншоты просмотри сам. FAIL сверь
   с кодом: ложный FAIL (неточный бриф, агент мерил не тот элемент) — исправь бриф, а не код.
4. **FAIL или PARTIAL по вине кода** — исправь, снова проверки п. 1 и новый прогон QA
   с новым именем сессии. После трёх прогонов с FAIL остановись и опиши пользователю, что
   не сходится.
5. **PASS** — отметь шаг `[x]` и допиши под ним строку итога: «QA <дата>: PASS — что и на каких
   размерах проверено (Storybook или `/settings`)». Отчёт лежит в `tmp/`, его нет в git, поэтому
   в плане — суть.
6. **Нужна проверка человеком** — то, что QA проверить не может: вход через провайдеров,
   сторонние сервисы и прод, реальные устройства (iOS Safari, Android), оценка вкуса и текста,
   то, что агент отметил BLOCKED не по вине кода. Проверенное QA отметь, как в п. 5, а на
   остаток заведи подшаг `N.x 🧑‍💻 Разработчик: проверить …` — что именно и почему без QA.
   Если остатка нет, подшаг 🧑‍💻 «проверить вживую» не заводи.
7. **QA не запустился** (обе модели в лимите, серверы не отвечают) — шаг не отмечай,
   допиши под ним «Ожидает QA: <причина>» и скажи пользователю.

Агент отмечает шаг `[x]`, если QA в итоге вернул PASS без ошибок и живая проверка не нужна
(п. 6) — в том числе шаг 🧑‍💻 «проверить …», который целиком проверил QA. Остальные шаги 🧑‍💻
(решения, сторонние сервисы, миграции, git) отмечает разработчик.
Шаги без интерфейса (документация, миграции, серверная логика без UI) QA не проходят:
проверки выбираются по типу задачи из `process.md`; для кода обязательны команды правила 5.

## Как запускать

- **Перед запуском** проверь, что серверы отвечают: `curl -s -o /dev/null -w '%{http_code}'
  http://localhost:3000` (и `:6006` для Storybook). Не отвечают — попроси пользователя запустить.
- **Бриф** клади в `tmp/qa-<шаг>/brief.md` (`tmp/` в `.gitignore`). В брифе: URL, критерии
  с буквами (A, B, …), размеры экрана, имя сессии браузера `qa-<шаг>-<n>` (новое на каждый
  прогон), каталог артефактов `tmp/qa-<шаг>/` и ограничения. Save на `localhost:3000`
  разрешён, но локальный сайт работает с боевой базой: агент меняет настоящий профиль
  пользователя. Удаление аккаунта запрещай в брифе всегда.
- **Вход.** Агент входит сессией пользователя из файла `tmp/qa-auth.json` (cookies и storage,
  `tmp/` в `.gitignore`). Файл создаётся один раз из Chrome пользователя, где он уже вошёл
  на `localhost:3000`: `agent-browser --auto-connect state save tmp/qa-auth.json`. В брифе
  укажи: «Первой командой открой страницу с `--state tmp/qa-auth.json`». Агент работает
  в своём отдельном браузере, но под учётной записью пользователя. Если с файлом `/settings`
  показывает Sign in, сессия истекла: попроси пользователя войти в Chrome и пересохрани файл.
  В файле — доступ к аккаунту: не копируй его из `tmp/` и не показывай содержимое. Supabase
  меняет refresh-токен при обновлении, поэтому после долгого прогона агента сессия
  пользователя в Chrome может закончиться — тогда ему нужно войти заново.
- **Сценарий с Save** (проверка требует сохранённых данных, например чек-лист на личной
  странице). До прогона сохрани снимок `curl -s localhost:3000/api/profiles/<username>`
  в `tmp/qa-<шаг>/profile-before.json`, после — сравни с текущим профилем. Не совпадает
  (агент упёрся в лимит шагов, не вернул состояние) — восстанови профиль сам через
  `agent-browser` и сверь снова. Сохранений в брифе — минимум, восстановление — отдельным
  шагом. `openai/gpt-6-luna` дважды отказалась нажимать Save на боевой базе даже с прямым
  разрешением (16.10.2026), такие сценарии сразу запускай на `opencode/gpt-6-luna`.
- **Запуск** — в фоне, прогон идёт несколько минут:

  ```sh
  opencode run --agent qa --model openai/gpt-6-luna --format json --title "QA <шаг>" \
    --file tmp/qa-<шаг>/brief.md "Проверь по приложенному brief.md и верни QA-отчёт." \
    > tmp/qa-<шаг>/events.jsonl 2> tmp/qa-<шаг>/stderr.log
  ```

- **Итог.** Код выхода `opencode run` — 0 даже при ошибке провайдера, ему не верь.
  Ошибки: `jq -c 'select(.type=="error") | .error' tmp/qa-<шаг>/events.jsonl`, отчёт:
  `jq -r 'select(.type=="text") | .part.text' tmp/qa-<шаг>/events.jsonl`. Отчёт без последней
  строки `QA_RESULT: …` — упавший прогон, а не результат проверки. Скриншоты из отчёта
  просмотри сам, прежде чем передавать вывод пользователю.
- **Если агент упал или завис:** останови процесс (фоновую задачу или `kill <pid>`; найти —
  `pgrep -fl "opencode run --agent qa"`), затем закрой его сессию браузера:
  `agent-browser session list` и `agent-browser --session <имя> close`. `close --all` не
  используй: он закроет чужие сессии.
- **Лимит модели.** Если `openai/gpt-6-luna` упёрлась в лимит (`usage_limit` в ошибке),
  перезапусти прогон с `--model opencode/gpt-6-luna` и новым именем сессии. Упала и она —
  не перезапускай в цикле, скажи пользователю.
